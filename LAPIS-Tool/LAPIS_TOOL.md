# LAPIS-Tool

This directory is the LAPIS-modified YASA tool tree.

## Role

`LAPIS-Tool` is the place to implement the YASA-side interfaces needed by the
LAPIS access-path propagation research prototype:

- load CTPC files generated by `LAPIS-Core`;
- add guarded access-path propagation edges during taint analysis;
- emit validation diagnostics for CTPC accept/reject feedback;
- run the same validation samples used by `LAPIS-Experiments`.

## Boundary

`/home/ubuntu/llm-yasa-repair/YASA-Engine-upstream` remains the untouched
baseline tool for comparison experiments. Do not make research changes there.

All YASA modifications for the LAPIS method should be made in this directory.

## Planned Integration Points

The first implementation target is a narrow CTPC hook for Python taint analysis:

1. Add a CTPC JSON loader.
2. Match CTPC structural guards against local UAST/taint facts.
3. Materialize additional propagation edges such as `dict.keys()[*] -> query`.
4. Emit diagnostics explaining which CTPC edge fired or was rejected.
5. Compare upstream YASA and LAPIS-enhanced YASA on the same validation samples.

## Current Access-Path Fact Engine

The current hook is enabled with:

```bash
--lapisCtpcFile /path/to/ctpc.json
```

The current implementation is an event-driven access-path fact engine wired into
the Python taint checker:

- assignment events record tainted symbols and derived access paths such as
  `args.keys()[*]`, preserved mapping keys, and formatted query variables;
- binary-operation events observe mapping-based percent-format consumers;
- guard facts record key whitelist/rejection conditions before later propagation
  steps consume them;
- sink checks consume the accumulated access-path facts to force or suppress
  findings according to the CTPC risk kind;
- write `lapis-ctpc-diagnostics.jsonl` under the YASA report directory.

## Structured CTPC v2 Interpreter

The tool now prefers structured CTPC v2 contracts when
`schema_version == "ctpc.v2"`. Instead of searching natural-language
conditions, the interpreter enables behavior by matching:

```text
propagation_edges[].event
propagation_edges[].pattern.kind
kill_conditions[].event
kill_conditions[].pattern.kind
applies_to.risk_kind
```

The first implemented pattern handlers are:

```text
dict_literal_key
dict_comprehension_key_preserved
return_fact_from_argument
percent_mapping_key
membership_rejection_guard
missing_mapping_key_fact
```

For the first PyMySQL feasibility case, those handlers cover dict-key to
mapping-key propagation, mapping-key preservation through dict comprehensions,
named percent-format propagation into SQL-structure risk, and kill guards.

The current implementation also keeps CTPC facts across file/function scopes so
the full PyMySQL case can connect the PoC assignment in `poc/...py` to the final
sink in `pymysql/cursors.py`.

Function-call behavior is expressed by structured CTPC summaries, not by a
callee-specific hard-code in the engine. A `return_fact_from_argument` summary
maps a caller actual argument fact, such as `arg0.keys()[*]`, to the call return
fact. The percent-format handler can then consume the returned mapping-key fact
from any callee described by CTPC, including `_escape_args(args, conn)` in the
PyMySQL case.

This is a structured extensibility point rather than a fully arbitrary CTPC DSL:
new datasets should express access-path repairs as CTPC v2 patterns, and the
YASA-side interpreter can then add focused handlers for new `pattern.kind`
families without changing the high-level LAPIS pipeline. Legacy CTPC v1 files
still work through a compatibility fallback.
